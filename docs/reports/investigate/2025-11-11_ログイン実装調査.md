# ログイン実装に関する調査レポート

日付: 2025-11-11

目的: ユーザ認証を実装し、ID: `yamada` / PW: `taro` でログインできるようにする方法を調査する。

参照: igakilab/springboot_samples を参考に調査を行った。
- リポジトリ: https://github.com/igakilab/springboot_samples
- Spring Security 公式ドキュメント: https://spring.io/guides/gs/securing-web/

調査で得られた要点

1. 依存関係
- igakilab のサンプルではセキュリティ関連の依存をコメントアウトしている箇所があるため、プロジェクトに追加または有効化する必要がある。

2. 自前でのユーザ定義方法
- 開発・検証段階では in-memory のユーザ定義（アプリ起動時に固定ユーザを登録）を使用するのが簡単で早い。
- 本件（ID: yamada, PW: taro）は in-memory で登録するのが適切。

3. パスワードの扱い
- Spring Security はパスワードをエンコードして保存・比較するのが標準（例: BCrypt）。
- 簡易検証のみであれば NoOp (平文) の PasswordEncoder を使うことも可能だが、本番では絶対に避けるべきである。

4. セキュリティ設定の実装箇所
- `SecurityConfig` のような設定クラスを追加し、認証（ユーザ登録）と認可（URLごとのアクセス制御）、フォームログインの設定を行う。
- Spring Boot 2.5.x 系（igakilab のサンプル世代）では `WebSecurityConfigurerAdapter` を利用した実装が多く見られる。
  - ただし、後続の Spring Security では別の設定方法（SecurityFilterChain を用いる）に移行している点に注意。

5. ログイン画面
- Thymeleaf のテンプレート（`src/main/resources/templates/`）にログインページを用意するか、Spring Security のデフォルトログインページを使う選択がある。
- igakilab サンプルは `static/index.html` を配置する例がある。ログイン機能をシンプルに動作確認するならデフォルトログイン画面で十分。

6. 静的リソースの扱い
- CSS/JS/画像などは `/static` に配置されるため、セキュリティ設定で静的リソースをホワイトリストにする必要がある（permitAll など）。

推奨実装手順（実装フェーズで行うこと）

2. セキュリティ設定クラスの追加
- パッケージ: `inuzuki.is.inujanken`（既存のアプリケーションパッケージに合わせる）
- クラス名: `SecurityConfig` など
- 内容（要点）: in-memory ユーザ `yamada` をパスワード `taro` で登録、パスワードエンコーダ（開発用は NoOp でも可、推奨は BCrypt）、フォームログインを有効化、静的リソースを permitAll に設定

3. 必要に応じてログインページ作成
- デフォルトページを使用する。

4. 実行と確認
- プロジェクトルート（`inujanken/`）で `gradle bootRun` を実行してアプリを起動。
- ブラウザで `http://localhost:8080/`（ポート未指定なら 8080）にアクセスする。
- ログイン画面が表示される場合は、ID `yamada` / PW `taro` でログインできることを確認する。

編集・変更が必要となるファイル一覧（想定）
- inujanken/src/main/java/inuzuki/is/inujanken/SecurityConfig.java (新規)

検証手順（Definition of Done の例）
- `inujanken/` ディレクトリで `gradle bootRun` を実行してアプリを起動できること。
- `http://localhost:8080/` にアクセスして認証画面が表示されること（デフォルトログイン画面でも可）。
- ID: `yamada` / PW: `taro` でログインに成功し、ログイン後のページ（アプリのトップ等）に遷移すること。
